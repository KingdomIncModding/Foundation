# Foundation 0.9.1 — framework and SDK implementation guide

**Status:** source implementation candidate. The supplied game-data ZIP includes the Kingdom Inc managed assemblies. BepInEx binaries and an installed Windows game executable are still required for packaging and gameplay verification. A compiled player DLL and runtime verification must be produced against a Kingdom Inc installation. **Do not rename or distribute the old 0.7.x binary as 0.9.1.**

## Architecture

- `Api/*` contains public contracts and mostly game-agnostic registries. Existing research, workspace, mod bar, and mod config contracts are retained.
- `Plugin/*` owns Harmony integration with Kingdom Inc, BepInEx lifecycle, UI, developer inspection, and game-specific smoke tests.
- `Examples/ExampleTechNodes` is an independent plugin that uses native research, native workspace nodes, native item pipes, and the Mod Bar. This is not shipped in the player package.
- `Examples/ExampleServices` is an independent plugin that demonstrates mod-owned save data, named signal sources, property selection, scoped event subscriptions, and config. It is not shipped in the player package.
- `FoundationApi` is the single SDK entry point. Other mods must reference the installed Foundation.dll without bundling their own copy.

### Existing functionality (retained)

BepInEx/Harmony, native research integration, per-mod research trees, category navigation, custom workspace node factory/build palette/placement, native IO buffers/pipes, expanded native Options/Mod Settings, native-style ModConfig template elements, and shared Mod Bar. Foundation does **not** reimplement the game's native flow item simulation.

### New functionality in this source revision

| API | Contract | Behavior |
| --- | --- | --- |
| Events | `FoundationApi.Events` | Typed publish/subscribe; disposable mod-owned listeners; exception isolation |
| Lifecycle | `FoundationApi.Lifecycle` | `NewKingdom`, `SaveLoaded`, `GameReady`, `BeforeSave`, `GameLeaving`; typed bus event `FoundationLifecycleEvent` |
| IO operations | `FoundationApi.IO` | Validate and connect/disconnect real item pipes within native workspace; record actual successful transfers |
| Flow inspection | `FoundationApi.Flow` | Native read-only element/port/pipe snapshots and item transfer events |
| Signals | `FoundationApi.Signals` | Register discoverable sources and exposed readable/writable properties; ~5 Hz main-thread change observation |
| Native signal selector | `section.AddSignalSelector` | Native-styled two-level source/property selection; Apply/Cancel staging; only explicitly exposed properties |
| Mod persistence | `FoundationApi.ModSave` | Versioned per-kingdom JSON inside `SaveGame` document; retain data from missing mods; callback isolation |
| Missing node recovery | `MissingWorkspaceElement` | Inert substitute when deserializing unknown node type; preserve original type ID, GUID, custom JSON, ports and pipe indices |
| Assets | `FoundationApi.Assets` | Owner-scoped PNG sprites and AssetBundles, with disposal |
| Mod scopes | `FoundationApi.ForMod(modId)` | Track and dispose registrations/subscriptions as one unit |
| Diagnostics | `FoundationApi.Diagnostics` | Recent bounded diagnostic history, mod ID, severity |
| Developer inspector | F8 (when enabled) | Unity IMGUI debug overlay showing workspace IO, measured transfer rate, signal sources, bus subscriptions and diagnostic history |

### IO does not imply signal flow

`FlowInput`, `FlowOutput`, and `FlowPipe` are the game's **item transport** system. `ISignalRegistry` exposes **named properties** for other mods and UI controls to discover. Signal values are read on the game thread and optional setters are explicitly supplied by the registering mod. The signal registry does not add hidden native ports, item slots, virtual throughput restrictions, or new simulation rules.

## Build on Windows

Place the repository in any source folder, with Kingdom Inc installed and BepInEx 5 available. Run PowerShell from the source folder, **with the game closed**:

```powershell
.\build-ready.ps1 -GameRoot 'C:\path\to\Kingdom Inc' -Verify -Install
```

This performs (1) `Foundation.csproj` Release build, (2) both consumer example builds, (3) isolated in-game diagnostics, (4) player/SDK archive creation and hash/extraction checks, (5) installation **only if previous steps succeed**. To build without launching the game, omit `-Verify` and `-Install`. For a compatibility run, add `-WithExistingPlugins` to the `-Verify` invocation. Use the `.\package.ps1 -GameRoot <...>` script separately to create versioned archives after a completed build.

`Releases/Foundation-0.9.1.zip` contains the player install files; `Releases/Foundation-SDK-0.9.1.zip` contains the SDK guide, compiled contracts, XML docs, and two example plugins. Neither archive contains the game's DLLs, BepInEx distribution, or game assets. `verify-isolated.ps1` runs against a junction/hard-link test sandbox and must not overwrite a live save.

## Core API examples

```csharp
using KingdomFoundation.Api;
using LightJson;

const string modId = "your.unique.mod.id";
FoundationModContext context = FoundationApi.ForMod(modId);

// Mod-owned source with two independently discoverable properties.
bool enabled = true;
int counter = 0;
context.Expose(new SignalSourceDefinition(modId, modId + ".controller", "My Controller", new[] {
    new SignalPropertyDefinition("enabled", "Enabled", typeof(bool), () => enabled, v => enabled = (bool)v),
    new SignalPropertyDefinition("counter", "Counter", typeof(int), () => counter)
}));

context.Listen<WorkspaceChangedEvent>(e => {
    if (e.Kind == WorkspaceChangeKind.Created) counter++;
});

context.Persist(2, () => new JsonObject { { "Counter", counter }, { "Enabled", enabled } },
    (schema, json) => {
        if (schema == 0 || !json.IsJsonObject) { counter = 0; enabled = true; return; }
        counter = json["Counter"].AsInteger;
        enabled = json["Enabled"].AsBoolean;
    });

var section = context.Settings("My Controller Mod", "Settings and signal binding");
section.AddToggle("Enabled", enabled, value => enabled = value, () => enabled);
SignalSelection selected = new SignalSelection(null, null);
section.AddSignalSelector("Signal", selected, value => selected = value, () => selected);

// At plugin teardown: context.Dispose();
```

### Saving and loading

`SaveGame.SaveCurrentState` is patched **after** vanilla serialization. Foundation appends `FoundationModData` and recomputes `Secret` using the native `SeedGenerator` algorithm; `SaveGame.LoadState` applies mod data only after a successful game load. Each entry has a version and a JSON value. Unknown mod entries are kept verbatim and re-serialized, not discarded. A provider with a newer schema is responsible for migrations in its `load(int previousSchema, JsonValue data)` callback. Source calls to save and restore should be on the main thread and should not mutate other mods' state. Schema `0` / `JsonValue.Null` resets the provider after a new kingdom or an older save without data.

Be aware that **the native game's `GamePlayer.ToJson/FromJson` method alone does not trigger Foundation's top-level mod persistence**. Use `SaveGame.SaveCurrentState` and `SaveGame.LoadState` for end-to-end tests.

### Missing custom workspace types

When a saved `FlowElement` refers to a type that cannot be resolved during deserialization, Foundation creates an **inert** `MissingWorkspaceElement`. It preserves the saved element's GUID, unknown JSON fields, input/output indices, and native port buffers; the missing node does **not** process items. Pipes attached to it are suspended while the mod is unavailable. Generic fallback rendering shows a warning label and approximate default dimensions (original custom prefab dimensions are not present in the native element save schema). This **does not** guarantee full preservation of unrecognized mod-defined upgrades or custom port behaviors. Make backup saves before uninstalling mods that own placed nodes.

### Real measured throughput

`FoundationApi.IO.GetMeasuredThroughput(pipe)` returns `TotalTransfers`, `TransfersLastTenSeconds`, and `AverageTransfersPerSecond` based on actual `WorldFlowPipe.ItemTransferred` callbacks. No invented per-port capacity/rate is exposed. Detached simulations and events before Foundation is initialized will not count toward these metrics. Data is kept only in memory.

### Diagnostics

Use the BepInEx Foundation configuration file to set `[Developer] EnableConsole = true`, restart the game, and press F8. The inspector shows the selected native workspace element's port state, registered sources/properties, bus subscriptions, and recent diagnostics. It uses Unity's debug IMGUI rather than the player's native menu theme; it is disabled by default and is not intended as a replacement for gameplay UI.

## Compatibility notes and limits

- Existing Foundation APIs from 0.8.0 remain accessible. The original 0.8.0 staged config behavior is unchanged: Save/Cancel applies to toggles, sliders, and dropdowns, while buttons are immediate.
- All method hooks are written against the provided decompiled Kingdom Inc source. This is **not** proof of binary equivalence with a specific installed game build.
- Only native item pipes are managed by `FoundationApi.IO`; abstract buses, automation control logic, multiplayer replication, Lua scripting, and cross-process service hosting are **not** provided here.
- Foundation is an in-process managed BepInEx plugin, not a sandbox. Executing untrusted third-party DLLs is not safe. Exception isolation covers callbacks, not arbitrary native/runtime memory corruption.
- Save-game preservation works by keeping unknown mod data and inert unknown nodes. As with all game-state patches, gameplay verification and backups are required before enabling it on a valued kingdom.
- Live hot-reload of DLL assemblies is not supported (BepInEx/Unity limitation). Disposing/re-registering a scoped configuration, event, signal, or UI element while the game runs is supported.
- AssetBundle compatibility and patch interoperation require testing with the installed Unity/game version; bundle contents and shaders remain mod-owned.

## Verification requirements for a stable release

1. Compile Foundation and both independent consumer examples against the installed game's managed DLLs.
2. Run `.\verify-isolated.ps1` without existing plugins, inspect test report and game log, then rerun with existing plugins.
3. Open the game's Tech Tree, Mod Settings, and workspace manually; verify native UI colors and layout, input buffering, pipe transfers and event tracking.
4. Test save/load across new game, autosave, explicit save, missing mod installation, and mod re-installation. Confirm unknown node JSON and pipes survive roundtrips.
5. Verify 0.8.0-compatible existing mods still load. Only after these steps publish version 1.0.0 as stable.
